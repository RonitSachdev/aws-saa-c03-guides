# Section 3: EC2 — Elastic Compute Cloud

## The idea

EC2 (Elastic Compute Cloud) is renting a computer in AWS's data center. That's it. You pick the size, you pick how you pay, you press launch, and seconds later you have a virtual machine (an "instance") with an IP address that you can SSH into.

Here's the analogy that makes the whole section click: **EC2 is a rental car agency.** The instance *family* is the car type — you don't rent a pickup truck to drive to a wedding, and you don't rent a Miata to haul furniture. The *purchasing option* is the rental contract — daily rate for a weekend trip, a yearly lease if you commute every day, or a crazy-cheap standby rate where the agency can take the car back with two minutes' notice. Almost every EC2 exam question is really asking one of two things: **which car?** or **which contract?**

Let's learn to answer both on sight.

## Instance families: which car?

The name tells you everything. Take **m5.2xlarge**:

```
 m        5       .2xlarge
 │        │        │
 family   generation  size
 (what    (newer =    (bigger = more
  it's     better $)   vCPU + RAM)
  good at)
```

Now the families, with mnemonics so they stick:

| Letter | Mnemonic | Good for | Exam keywords |
|---|---|---|---|
| **M** | **M**iddle-of-the-road | General purpose, balanced CPU:RAM | "web app server", no special demands |
| **T** | **T**urbo (burstable) | Spiky, mostly-idle workloads | "occasional spikes", "dev/test", CPU credits |
| **C** | **C**PU / Compute | CPU-hungry work | "batch processing", "encoding", "HPC", "gaming servers" |
| **R** | **R**AM | Memory-hungry work | "in-memory cache", "real-time big data analytics" |
| **X** | e**X**treme RAM | Massive in-memory databases | **"SAP HANA"** — this word alone means X family |
| **I** | **I**OPS | Fast local NVMe storage | "high random I/O", "NoSQL needing local disk" |
| **D** | **D**ense **D**isk | Lots of local HDD storage | "distributed file systems", "data warehousing" |
| **P** | GPU (**P**ower training) | **ML model training** | "train a deep learning model" |
| **G** | GPU (**G**raphics) | Graphics rendering, ML **inference** | "video rendering", "game streaming" |
| **Inf** | **Inf**erence | Purpose-built ML inference chips | "cost-effective inference at scale" |

AWS groups these letters into **five categories**, and the exam often uses the category name instead of the letter:

| Category | Families | Signal |
|---|---|---|
| **General Purpose** | M, T | web servers, dev environments, general apps |
| **Compute Optimized** | C | compute-intensive work |
| **Memory Optimized** | R, X | big in-memory datasets and analytics |
| **Accelerated Computing** | P, G, Inf | **GPUs / FPGAs** / specialized hardware |
| **Storage Optimized** | I, D | **high sequential read/write to very large local datasets** (e.g., log processing), tens of thousands of low-latency random IOPS |

**THE trap:** *"high sequential read and write access to very large data sets on local storage"* → **Storage Optimized**, NOT Memory Optimized. "Large dataset" tempts you toward RAM, but "local storage + sequential I/O" is the disk family.

And one magic suffix: a **g** after the generation number (like **m7g**, **c7g**) means **Graviton — AWS's own ARM processor**. The exam signals for Graviton are **"best price-performance"**, **"reduce compute cost"**, or **"sustainability"**. See those words with a Linux workload that can run on ARM? Answer: Graviton.

### The T-family trap (learn this cold)

T instances are "burstable." Think of a phone battery: while the instance idles, it **earns CPU credits**; when load spikes, it **spends credits** to burst above its tiny baseline. Great for workloads that are quiet most of the day.

**THE trap:** *"Our t3 instance was fine for hours, then performance degraded under sustained load."* What happened? **Credits ran out → the instance is throttled down to its baseline CPU.** The fix depends on the workload:

- Sustained, steady load → **move to an M or C family** (they don't play the credit game).
- Keep the T instance but never throttle → enable **T Unlimited mode**, which lets it keep bursting and **bills you for the overage**.

Corollary trap: *"We enabled a setting and now the bill increased during a traffic spike"* → that's **Unlimited mode overage charges**. Bursting past credits isn't free — it's a loan.

## Purchasing options: which contract?

This is the most-tested pricing topic on the exam. The decision hinges on two words in the question: **how long** and **how interruptible**.

| Option | Discount | Commitment | When the exam wants it |
|---|---|---|---|
| **On-Demand** | none | none | Short-term, **unpredictable**, can't commit. **Anything under 1 year** → On-Demand, because RIs/Savings Plans start at 1 year |
| **Reserved Instances** | up to **72%** (Standard) | **1 or 3 years** | Steady, predictable, long-running (e.g., a database that runs 24/7) |
| **Convertible RI** | up to **66%** | 1 or 3 years | Steady load but **"instance family might change"** — you trade discount for flexibility |
| **Savings Plans** | ~same as RI | commit **$/hour** for 1 or 3 years | Steady **spend**, flexible everything else |
| **Spot** | up to **90%** | none — AWS can reclaim with a **2-minute warning** | Fault-tolerant, stateless, batch, interruptible |
| **Dedicated Host** | pricey | a whole physical server | **BYOL** (bring your own license) with **per-socket / per-core** licensing |
| **Dedicated Instance** | cheaper than Host | isolated hardware | "Must not share hardware with other customers" but no license/visibility needs |

Now the nuances the exam actually tests:

**Zonal RI = discount AND a seat reservation.** A regular (regional) RI is just a billing discount. But a **zonal RI** — one scoped to a specific Availability Zone — **also reserves capacity** in that AZ. So *"we must guarantee capacity will be available for our month-end batch run"* → **zonal RI or an On-Demand Capacity Reservation**. **Savings Plans never reserve capacity** — they are billing constructs only. That distinction is a favorite trick.

**The capacity-vs-discount grid** (worth memorizing as a table):

| Option | Term | Reserves capacity? | Billing discount? | Instance limits |
|---|---|---|---|---|
| **On-Demand Capacity Reservation** | **none** — any duration, cancel anytime | ✅ yes (one AZ) | ❌ none by itself — **pair with a Savings Plan or regional RI** for the discount | your On-Demand limits |
| **Zonal RI** | 1 or 3 years | ✅ yes | ✅ yes | 20 per AZ |
| **Regional RI** | 1 or 3 years | ❌ no | ✅ yes | 20 per Region |
| **Savings Plans** | 1 or 3 years | ❌ no | ✅ yes | no limit |

So *"guarantee capacity for a short event, no long-term commitment"* → **On-Demand Capacity Reservation** (billing starts when it goes active and stops when you cancel it). *"Guarantee capacity AND get a discount for 3 years"* → **Zonal RI**.

**RI fine print the exam likes:**
- When an RI **expires**, the instances it covered keep running but are **billed at On-Demand rates** — the discount silently disappears.
- **Terminating** an instance does **not** cancel its RI — you **keep paying until the term ends**.
- An RI is scoped to **one Region (or one AZ)**; one purchase can't cover several Regions.
- **Convertible RIs** can be exchanged only for **other Convertible RIs**.
- Unused **Standard RIs** can be sold on the **Reserved Instance Marketplace**; Convertible RIs can't.

**Billing granularity:** On-Demand Linux/Windows instances are **billed per second** (60-second minimum). The old "billing hour" is legacy. While an instance is **stopping to hibernate you ARE billed**; while it's **stopping to stop, you are not**. On-Demand capacity is capped by a **vCPU-based limit per Region** — if you hit it, **request a limit increase**; you don't need to move Regions.

**Savings Plans come in two flavors:**
- **Compute Savings Plan** — applies to **any instance family, any region, and even Fargate and Lambda**. Maximum flexibility, slightly smaller discount. Keyword: *"flexibility to change instance types and regions."*
- **EC2 Instance Savings Plan** — locked to **one family in one region** (e.g., "m5 in us-east-1"), but a **bigger discount**. Keyword: *"committed to this family, wants the largest savings."*

**Spot rules of engagement.** Up to 90% off, but AWS can pull the instance with a **2-minute interruption notice**. So Spot fits work that is **stateless, fault-tolerant, checkpointable, batch, or deadline-flexible**: image rendering, CI builds, big data analytics, containerized workers. **NEVER** put databases or anything critical/uninterruptible on Spot — *"cannot tolerate interruption"* in a question is a flashing sign that Spot is the wrong answer, no matter how much the question emphasizes cost.

**The classic combo:** *"predictable baseline traffic plus unpredictable surges, minimize cost"* → **Reserved Instances (or a Savings Plan) for the baseline + Spot (or On-Demand) for the surge**.

**Host vs Instance.** Both give you hardware not shared with other AWS customers. The difference:
- **Dedicated Host** — you get **visibility into the physical server itself: sockets, cores, host ID**. That's exactly what **per-socket or per-core BYOL licenses** (old-school Windows Server, SQL Server, Oracle licenses) require. **The word "socket" or "BYOL" in the question = Dedicated Host.**
- **Dedicated Instance** — hardware isolation, but **no visibility or control over the physical server**, and cheaper. Compliance-only isolation, no licensing story. Fine print: a Dedicated Instance **may share hardware with non-dedicated instances from your own account** — it's isolated from *other customers*, not from you.

## Placement groups: where the cars park

Three strategies. Mnemonic: **Cluster = Close, Spread = Solo, Partition = Packs.**

```
CLUSTER (Close)          SPREAD (Solo)            PARTITION (Packs)
┌─────────────┐          ┌──┐ ┌──┐ ┌──┐           ┌────┐ ┌────┐ ┌────┐
│ ▪ ▪ ▪ ▪ ▪ ▪ │          │▪ │ │▪ │ │▪ │           │▪▪▪ │ │▪▪▪ │ │▪▪▪ │
│  same rack  │          └──┘ └──┘ └──┘           └────┘ └────┘ └────┘
└─────────────┘          each its own rack        isolated rack groups
lowest latency           max 7 per AZ             7 partitions per AZ
```

- **Cluster** — everything packed on the **same rack** in one AZ. **Lowest latency, highest throughput.** Keyword: **HPC, tightly-coupled, node-to-node network performance**. Risk: rack dies, everything dies.
- **Spread** — every instance on **its own rack** with its own power/network. Maximum blast-radius isolation, but capped at **7 instances per AZ**. Keyword: **small number of critical instances that must not fail together**.
- **Partition** — up to **7 partitions per AZ**, each partition is an isolated group of racks, and each partition can hold **hundreds of instances**. A rack failure takes out one partition, not the fleet — and the instances can **read their partition placement from instance metadata**, which topology-aware software uses. Keywords: **Hadoop, Cassandra, Kafka, HDFS** — big distributed systems.

**THE trap:** *"critical fleet of 20 instances, each must be isolated from hardware failure"* — Spread sounds right but caps at 7 per AZ; either spread across 3 AZs (7+7+6 works) or the answer is Partition. Count the instances.

**Capacity errors in a placement group.** Best practice: launch **all the instances you need in a single launch request, all the same instance type**. Adding instances later or mixing types raises the odds of an **insufficient capacity error**. If you hit one while the group already has running instances → **stop and start all instances in the group, then retry** (the restart can migrate them onto hardware with room for everyone). Cluster and partition groups have no fixed instance limit; only Spread is capped at 7 per AZ.

## ENI: the detachable network identity card

An **Elastic Network Interface (ENI)** is a virtual network card, and here's the key mental model: it's a **detachable identity badge**. The ENI carries the **private IP address, MAC address, and security groups** — not the instance. Detach the badge from a failed instance, clip it onto a standby instance, and the standby instantly answers to the **same private IP**.

That's the exam's favorite **failover trick**: *"on failure, redirect traffic to a standby instance without changing the IP the clients use"* → **move the ENI**.

**THE trap:** an ENI lives in one subnet, so **it can only move to an instance in the SAME Availability Zone**. Cross-AZ failover with an ENI is impossible — for that you need DNS, a load balancer, or Route 53.

One more pattern: attaching **multiple ENIs** to one instance = **dual-homing** — for example, one interface on the public network and one on a separate **management network**.

### Enhanced networking: ENA, EFA, and Nitro

- **Enhanced networking** uses **SR-IOV (single root I/O virtualization)** to give higher bandwidth, higher packets per second (PPS), and lower, more consistent inter-instance latency — at **no extra charge**.
- **ENA (Elastic Network Adapter)** — the standard enhanced-networking device, **up to 100 Gbps** on supported types (more on the newest network-optimized types). It provides the normal IP networking that VPCs need. The **Intel 82599 VF** interface (up to 10 Gbps) is the **legacy** option.
- **EFA (Elastic Fabric Adapter)** — everything ENA does **plus OS-bypass**, which lets HPC and ML apps (MPI, NCCL) talk directly to the network hardware for ultra-low-latency **inter-node communication**. Signal: *"tightly-coupled HPC / MPI"* → **EFA + Cluster placement group**. **THE trap: EFA's OS-bypass is NOT supported on Windows** — Linux only.
- **ENI vs ENA vs EFA:** ENI = a virtual network *card* (identity: IP, MAC, SGs, above); ENA = *fast* networking; EFA = *HPC* networking.
- **Nitro System** — AWS's hardware virtualization platform under every current-generation instance. It offloads networking, storage, and security to dedicated hardware, which unlocks things like the highest EBS IOPS and enhanced networking.

## Elastic IP: the phone number you own

**THE trap first, because it's tested constantly:** the default auto-assigned **public IP changes every time you stop and start the instance**. (It survives a reboot, but stop/start = new IP.) So *"clients could no longer reach the server after maintenance stop/start"* → the public IP changed → the fix is an **Elastic IP**.

An **Elastic IP (EIP)** is a static public IPv4 address that **you own** and can remap to any instance — **even across AZs** (unlike an ENI move). The fine print:

- **Charged when NOT attached** to a running instance (idle = billed — AWS wants you using them or releasing them).
- Soft limit of **5 per region**.
- Classic use: **mask an instance failure** by remapping the EIP to a standby instance — clients keep the same address.
- **Best practice per the exam:** avoid EIPs when you can — put a **load balancer with a DNS name** in front, or use **Global Accelerator** (which gives you 2 static anycast IPs). "Architect wants to avoid Elastic IPs" → ELB + DNS.

## Boot-time toolkit: user data, metadata, hibernate

- **User data** — a script you paste at launch. It **runs once, at first boot, as root**. Keyword: *"automatically install/configure software when the instance launches"* → user data. (Runs every boot? No — once. Need every boot, you'd modify cloud-init config, but the exam wants "once at launch.") Because it runs as root, the script **doesn't need `sudo`**. You **can't change user data while the instance is running** — stop it first.
- **Instance metadata** — from inside the instance, hit **`http://169.254.169.254/latest/meta-data/`** to learn about yourself: instance ID, AZ, attached IAM role credentials, partition number. Memorize that IP. **IMDSv2** is the hardened version: it requires a **session token first** (a PUT request, then use the token), which blocks the SSRF attacks that plagued v1. "Protect metadata from SSRF" → **enforce IMDSv2**.
- **Hibernate** — instead of stopping cold, the instance's **RAM is written to the encrypted EBS root volume**; on start, RAM is restored and the app resumes mid-thought. Keywords: *"long-running in-memory state"*, *"reduce boot time / pre-warmed caches"*. Requirements: root volume must be **encrypted EBS**, and RAM must fit on it.

### AMIs: the car's factory image

An **AMI (Amazon Machine Image)** is the template an instance boots from: OS, installed software, and block-device mapping.

- **AMIs are Region-bound.** To launch the same image in another Region (for example, for **disaster recovery**), you must **copy the AMI** to that Region first.
- **Golden AMI** — a standardized, **patched, hardened** image your organization approves. The boot-speed pattern is **hybrid**: bake the **static** parts (OS, packages, agents) into the golden AMI and do only the **dynamic** parts (fetch config, join cluster) in **user data** at boot. *"Reduce instance boot/bootstrap time"* → **golden AMI**, not a longer user data script.
- **Instance-store-backed AMI** — the root volume lives on **instance store**, so the instance **cannot be stopped** (only rebooted or terminated) and its **data is gone on termination**. EBS-backed AMIs are the default and what you want almost always.

## Question patterns

> *"Nightly batch job processes images; jobs can be re-run if they fail; minimize cost"* → **Spot instances** (fault-tolerant + interruptible + cheapest = Spot's home turf)

> *"Critical payment workload, cannot tolerate interruption, minimize cost"* → **NOT Spot — Reserved Instances / Savings Plan** ("cannot tolerate interruption" disqualifies Spot no matter how loudly the question says "cheapest")

> *"SAP HANA in-memory database on EC2"* → **X family** (eXtreme RAM; plain "in-memory cache/analytics" → R family)

> *"Train a deep learning model" vs "serve ML predictions cheaply"* → **P family for training, G or Inf for inference** (P = Power training, G/Inf = inference/graphics)

> *"Company has per-socket Windows Server licenses to bring to AWS"* → **Dedicated Host** (sockets/cores/BYOL = Host; mere hardware isolation = Dedicated Instance)

> *"Must guarantee EC2 capacity is available in a specific AZ for month-end processing"* → **Zonal Reserved Instance or On-Demand Capacity Reservation** (Savings Plans and regional RIs are billing-only — they hold no seats)

> *"t3 instance performs well, then slows dramatically after hours of sustained load"* → **CPU credits exhausted, throttled to baseline — move to M/C family or enable Unlimited mode** (and "bill spiked after enabling a setting" = Unlimited overage)

> *"After stopping and starting the instance, users can't reach it at the old address"* → **Public IP changed on stop/start — assign an Elastic IP** (default public IPs are not sticky)

> *"On primary failure, standby must take over with the same private IP, no client changes"* → **Move the ENI to the standby** (works only within the **same AZ**)

> *"Tightly-coupled HPC workload needs the lowest inter-node latency"* → **Cluster placement group** (Close = same rack; Kafka/Cassandra/Hadoop at scale = Partition; 7 critical solo instances = Spread)

> *"Steady $ commitment but wants freedom to switch families, regions, and even Fargate/Lambda"* → **Compute Savings Plan** (one family, one region, max discount = EC2 Instance Savings Plan)

> *"Predictable baseline + unpredictable spikes, optimize cost"* → **RI/Savings Plan for baseline + Spot for the spikes** (the classic combo)

> *"Need guaranteed capacity in one AZ for a two-week event, no 1-year commitment"* → **On-Demand Capacity Reservation** (no term; add a Savings Plan/regional RI if you also want a discount)

> *"Our 3-year RI ended and the bill jumped, though nothing changed"* → **RI expired → instances now billed On-Demand** (renew or buy a Savings Plan)

> *"Launch the same server image in another Region for DR"* → **Copy the AMI to that Region** (AMIs are Region-bound)

> *"Instances take too long to bootstrap at scale-out"* → **Golden AMI with static software baked in + small user data for dynamic config**

> *"HPC/MPI app needs OS-bypass, lowest inter-node latency"* → **EFA (Linux) + Cluster placement group** (EFA OS-bypass isn't supported on Windows; plain high bandwidth = ENA)

> *"Insufficient capacity error adding instances to an existing placement group"* → **Stop and start all instances in the group, then retry** (and next time launch them all in one request, same type)

> *"Large sequential reads/writes to huge local datasets, e.g., log processing"* → **Storage Optimized** (not Memory Optimized)
