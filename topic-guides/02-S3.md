# Section 2: S3 — Simple Storage Service

## The idea

S3 is where AWS keeps *stuff*. Not a hard drive, not a filesystem — an **object store**. Think of it as an **infinite valet parking garage for files**: you hand over your file (the "object"), you get a claim ticket (the "key" — its full name, like `photos/2026/cat.jpg`), and whenever you come back with the ticket, you get the whole file back. You can't pop the hood and change the engine while it's parked — **you can't edit a byte in the middle of an object; you replace the whole object**. That's the core difference from a disk (that's EBS) or a shared network filesystem (that's EFS).

Objects live in **buckets**. **Bucket names are globally unique across all of AWS** (no two customers anywhere can have the same bucket name), but **the bucket itself lives in one region** you choose. Capacity is unlimited; a single object maxes out at **5 TB**. For big uploads, **multipart upload** splits the file into parallel chunks — **recommended over 100 MB, REQUIRED over 5 GB** (a single PUT caps at 5 GB). S3 promises **eleven 9s of durability** (99.999999999% — your data essentially never evaporates) across every storage class; what varies between classes is cost, availability, and how fast you can get things back.

Vocabulary the exam assumes: **bucket** (globally unique name, one shared namespace across all accounts) → **object key** (the unique name inside the bucket) → **object metadata** (name-value pairs describing the object) → **object tags** (key-value pairs to categorize objects, usable in lifecycle and IAM rules).

Two behaviors worth knowing:

- **Consistency:** S3 has been **strongly read-after-write consistent** for all PUTs, overwrites, deletes, and LIST operations **since December 2020**. Read it right after writing it and you get the new data. (Older study material that describes "eventual consistency": a new object missing from LIST, or an overwrite returning stale data, is **outdated**. Don't pick it.)
- **Concurrent writes:** two simultaneous PUTs to the **same key** → the one with the **latest timestamp wins**. S3 has **no built-in locking for concurrent updates** (Object Lock is WORM retention, not a mutex). If that matters, build the locking into your application.
- **Requester Pays** bucket: the **requester** pays for requests and data download; the **bucket owner still pays for storage**.

That "how fast can I get it back and how much does it cost" question is the heart of the exam's S3 questions, so let's build the machine that answers all of them.

## Storage classes and THE 3-filter algorithm

The classes, top shelf to deep freeze:

| Class | Retrieval | Min storage duration | Use when |
|---|---|---|---|
| **Standard** | milliseconds | none | Frequently accessed, hot data |
| **Intelligent-Tiering** | milliseconds | none | **Unknown/unpredictable** access patterns |
| **Standard-IA** | milliseconds | **30 days** | Infrequent access, needs instant retrieval |
| **One Zone-IA** | milliseconds | 30 days | Infrequent AND **re-creatable** (one AZ only!) |
| **Glacier Instant Retrieval** | **milliseconds** | **90 days** | Archive touched ~quarterly, needed instantly |
| **Glacier Flexible Retrieval** | Expedited **1–5 min** / Standard **3–5 hr** / Bulk **5–12 hr** | 90 days | Archive, minutes-to-hours retrieval OK |
| **Glacier Deep Archive** | Standard **12 hr** / Bulk **48 hr** | **180 days** | Cheapest. Retrieval is HOURS — **can NEVER beat 12 hr** |

("IA" = Infrequent Access; "AZ" = Availability Zone, one physical data-center cluster.)

The fine print for the four millisecond-access classes (all have **11 9s durability** and **millisecond first-byte latency**):

| | Standard | Standard-IA | One Zone-IA | Intelligent-Tiering |
|---|---|---|---|---|
| Availability (designed) | **99.99%** | 99.9% | **99.5%** | 99.9% |
| Availability SLA | 99.9% | 99% | 99% | 99% |
| AZs | ≥ 3 | ≥ 3 | **only 1** | ≥ 3 |
| Minimum billable object size | none | **128 KB** | **128 KB** | none (but < 128 KB never tiered) |
| Retrieval fee | none | **per GB retrieved** | **per GB retrieved** | none |

Standard-IA costs more than One Zone-IA because it stores data redundantly across AZs. **IA is not for archiving.** Archives belong in the Glacier family.

**Hot / warm / cold vocabulary:** hot storage = frequently accessed data, warm = less frequently accessed, cold = rarely accessed. **The colder the data, the cheaper it is to store and the costlier it is to access.**

Every "most cost-effective storage class" question yields to the same three filters:

**Filter 1 — access frequency picks the family.** Daily/constant → Standard family. Monthly-ish → IA. A few times a year → Glacier family. Unknown → Intelligent-Tiering.

**Filter 2 — the retrieval-time requirement eliminates classes.** *"Needed immediately / within milliseconds"* kills Flexible and Deep Archive (Glacier **Instant** survives — it retrieves in milliseconds). *"Within minutes/hours"* — Flexible is fine (Expedited 1–5 min, Standard 3–5 hr, Bulk 5–12 hr). *"Within 12 hours or more"* — now Deep Archive is on the table. Burn this in: **Deep Archive can NEVER deliver faster than 12 hours.** Any deadline under 12 hours disqualifies it, no matter how cheap it is.

**Filter 3 — minimum storage duration.** IA classes bill a minimum **30 days**, Glacier Instant and Flexible **90 days**, Deep Archive **180 days** — delete early and you pay for the minimum anyway. **Data that lives (or is only kept) under 30 days → plain Standard wins**, because every "cheaper" class charges you 30+ days regardless.

**Cheapest class that survives all three filters wins.** Worked example: *"accessed twice a year, auditors need it within 10 minutes, most cost-effective"* → twice a year = Glacier family; "10 minutes" kills Deep Archive (12 hr floor) but Flexible's Expedited (1–5 min) passes; Instant also passes but costs more → **Glacier Flexible Retrieval**.

Glacier extras that show up as answer choices:

- **Provisioned capacity**: makes sure **Expedited** retrieval capacity is there when you need it. Each unit guarantees **at least 3 Expedited retrievals every 5 minutes** and **up to 150 MB/s** of retrieval throughput. Signal: *"Expedited retrievals must ALWAYS be available / never be rejected."*
- **Glacier Select**: run simple SQL filters **directly on archived data** without restoring the whole archive first.
- **THE trap: Athena can't query objects sitting in Glacier Flexible Retrieval or Deep Archive.** You have to restore them first. If the data must stay queryable by Athena, keep it in **Standard-IA** (or Glacier Instant Retrieval) instead of archiving it.
- **Vault Lock** (for Glacier vaults): a vault can have one access policy plus one **Vault Lock policy**. A Vault Lock policy is an access policy you **lock**, and once locked it's immutable. Signal: *"enforce regulatory/compliance controls on the archive vault."*

## The two "special" classes and their exact signals

**One Zone-IA** stores data in a **single Availability Zone** — the AZ burns down, the data is gone. So it's ~20% cheaper and correct **ONLY when the data is re-creatable or a secondary copy**: thumbnails you can regenerate, a replica of on-prem data, secondary backups. The exam signal is the phrase **"can be regenerated / re-created / is a secondary copy."** No such phrase → do not pick One Zone.

**Intelligent-Tiering** watches each object and moves it between tiers automatically. Sounds like a free lunch; it isn't:

- There's a **monitoring fee per object** — millions of tiny objects = real money.
- **Objects under 128 KB are never tiered** (they just sit at Standard rates).
- An object pays **Standard price for ~30 days** of observed inactivity before IT moves it down.

So: **if you KNOW the pattern ("accessed heavily for 30 days, then rarely"), a lifecycle rule beats Intelligent-Tiering** — it's cheaper and deterministic. IT is correct **ONLY when the question says access is unknown, unpredictable, or changing**.

## Lifecycle, versioning, replication

**Lifecycle rules** = the automated conveyor belt: *transition* actions move objects down the class ladder on a schedule ("after 30 days → Standard-IA, after 90 → Glacier, after 365 → delete"), *expiration* actions delete them. Also great for cleaning up old versions and **aborting incomplete multipart uploads** (which silently cost money forever otherwise).

**THE lifecycle timing trap:** objects must sit in Standard for **at least 30 days** before a lifecycle rule can move them to **Standard-IA or One Zone-IA**. A rule like "move to Standard-IA after 7 days" is invalid. Transitions straight to the **Glacier classes have no 30-day floor**, so "move to Glacier Flexible / Deep Archive after 7 days" (or even day 0) is fine. Remember the Glacier minimum-duration charges still apply after the move.

**Versioning** keeps every version of every object. Overwrite = new version on top; delete = a **delete marker** placed on top (the old versions are still there — remove the marker and the object "reappears"). It's the answer to *"protect against accidental overwrite/deletion."* Once enabled, you can only suspend it, never fully un-enable. Add **MFA Delete** and permanently deleting a version (or suspending versioning) requires the **root user's MFA device** — the "extra protection against accidental or malicious deletes" answer.

**Replication** copies objects to another bucket automatically:

- **CRR** (Cross-Region Replication) → different region: compliance, disaster recovery (it **protects against a full regional outage**, which versioning alone can't), lower latency for far-away users.
- **SRR** (Same-Region Replication) → same region: log aggregation into one bucket, prod → test copies.
- Requires **versioning ON in both buckets**.
- **THE trap:** replication copies **NEW objects only**, from the moment you enable it. *"Existing objects must be replicated too"* → **S3 Batch Replication**.

## The encryption ladder (sorted by how little you trust AWS)

Quick jargon: encryption **at rest** = scrambled while sitting on disk. Encryption **in transit** = scrambled while traveling over the network, done by **TLS** (Transport Layer Security — the "s" in https, the standard protocol that encrypts web traffic). **KMS** = AWS Key Management Service, the managed vault for encryption keys.

Climb the ladder as trust in AWS decreases and your effort increases:

| Rung | Who holds the key | Why pick it |
|---|---|---|
| **SSE-S3** (AES-256) | AWS, fully managed | **Default** on all new objects. Zero effort. "Just encrypt it" |
| **SSE-KMS** | A KMS key you control in your account | **Audit every key use in CloudTrail**, control rotation, decide who may decrypt. **"Audit" is its keyword** |
| **SSE-C** | **You** supply the key **on every request** | AWS's CPUs do the encrypting but never store your key; key travels per request **over HTTPS** (mandatory) |
| **Client-side** | You, entirely | You **encrypt BEFORE upload; AWS never sees plaintext**, ever |

(SSE = Server-Side Encryption — S3's servers do the crypto work for the first three rungs.)

Rung details:

- **SSE-S3** uses **AES-256**. Each object is encrypted with a unique key, and that key is itself encrypted with a root key that AWS rotates regularly. S3 server-side encryption is **AES-256 only**, so an answer offering "AES-128" is a distractor.
- **Client-side** encryption: either use a **KMS key** to get data keys, or keep a **root key in your own application** and never send it to AWS. Client-side is also the answer when you must use **your own proprietary encryption algorithm**.

SSE-KMS fine print worth points: heavy traffic can hit **KMS API request limits** (every object touch calls KMS). **S3 Bucket Key** fixes this — one bucket-level key cuts **KMS API costs ~99%** — BUT fewer KMS calls means a **coarser per-object audit trail** in CloudTrail. Cost fix with an audit trade-off.

Three encryption traps:

- **"Encrypt in transit" = TLS/HTTPS**, not KMS. Don't let a KMS answer seduce you on a transit question.
- **Enforce HTTPS** → bucket policy that **Denies** requests where **`aws:SecureTransport` = `false`**. Classic exam answer, verbatim.
- Turning encryption on **does not touch existing objects** — encryption applies at write time. *"Encrypt all EXISTING objects"* → **S3 Batch Operations** (re-writes them encrypted).

## Object Lock: WORM

**Object Lock** makes objects **WORM** — Write Once, Read Many: written, then **impossible to delete or overwrite** for a set retention period. Requirements: **versioning must be on**, and Object Lock can only be enabled **at bucket creation time** (exam loves this detail).

| Mode | Who can delete during retention | Exam signal |
|---|---|---|
| **Compliance mode** | **NOBODY. Not admins, not even root.** Period. | "regulators require," "even administrators must not delete" |
| **Governance mode** | Users with a special bypass permission | "protected, but privileged users may override" |
| **Legal Hold** | No one, **indefinitely — no expiry date, stays until explicitly removed** | "**lawsuit**," litigation, "until the case closes" |

**THE trap:** "even administrators / even the root user cannot delete" → **Compliance**, never Governance.

More Object Lock fine print:

- **One-way door:** once a bucket has Object Lock enabled, you **can't disable Object Lock** and **can't suspend versioning** on it.
- **Retention period** = a fixed amount of time an object version is protected. A **legal hold has no time period**; it stays until someone with `s3:PutObjectLegalHold` removes it.
- Retention and legal hold are **independent and can be stacked** on the same object version. A legal hold **keeps blocking deletes/overwrites even after the retention period has expired**.

## Who can get in: access controls

- **Block Public Access** — the master kill-switch, **on by default**, overrides any policy or ACL that tries to make things public. *"Bucket policy allows public read but access still fails"* → Block Public Access is on. *"Guarantee nothing is ever public org-wide"* → keep it on everywhere.
- **Bucket policies** — resource-based JSON policies (Section 1!) on the bucket: cross-account grants, enforce HTTPS, require encryption headers, IP restrictions.
- **Presigned URLs** — a time-limited signed link to one object: *"let a customer download this private file for 20 minutes, no AWS account needed."* The URL **inherits the permissions of whoever created it** (creator can't read it → URL doesn't work either) and lives **at most 7 days**.
- **OAC (Origin Access Control)** — when CloudFront (AWS's CDN — content delivery network, a global fleet of caching edge servers) sits in front of your bucket, OAC lets **only CloudFront** fetch from the bucket, so nobody can bypass the CDN and hit S3 directly. Signal: *"users must access content only through CloudFront."* (You may see the older name OAI — OAC is the current answer.)
- **S3 presigned URL vs CloudFront signed URL:** a presigned URL hits S3 **directly and bypasses CloudFront**. If content is served through CloudFront, use **CloudFront signed URLs** (one file) or **signed cookies** (many files) instead. Presigned URLs also don't scale when many users need many files. See Section 8.
- **Cross-account access**: either a **bucket policy** that grants the other account, or an **IAM role in the bucket's account** that the other account assumes.
- **Object ownership (the cross-account upload trap):** by default an object is **owned by the account that uploaded it**, even if it's in your bucket, so the bucket owner may not be able to read it. Classic fix: require the **`bucket-owner-full-control` canned ACL**, enforced in the **bucket policy** (not an IAM policy). Modern fix: set **S3 Object Ownership = Bucket owner enforced**, which disables ACLs and makes the bucket owner own everything automatically.
- **ACLs (legacy):** they can grant access only to **other AWS accounts or predefined groups, not to individual IAM users**. They're **disabled by default** on new buckets (Bucket owner enforced). AWS recommends policies instead, so treat ACL-based answers as legacy unless the question forces them.
- **S3 Access Points**: named entry points to a bucket, each with its own policy. You can configure one to **accept requests only from a specific VPC**. Signal: *"restrict S3 data access to a private network / per-application access policies on a shared bucket."*
- **VPC endpoint policy**: to limit which S3 buckets instances in a VPC may reach (*"only trusted buckets"*), write **one endpoint policy on the gateway endpoint**. That's far less work than editing every bucket's policy.
- **S3 has no security groups.** Network-level control comes from endpoint policies, Access Points, and bucket-policy conditions such as `aws:SourceVpce` / `aws:SourceIp`.
- **MFA-protected API access**: a bucket-policy condition (`aws:MultiFactorAuthPresent`) that requires MFA-authenticated requests. This is separate from **MFA Delete** (versioning).
- **CORS (Cross-Origin Resource Sharing)**: lets browser JavaScript from **one domain** load objects from a bucket served on **another domain** (for example, a web page on `palawan.com` loading assets from `travel.cebu.com`). **CORS does not make objects public.** It only relaxes the browser's same-origin rule.
- **Static website hosting**: S3 serves **static content only (HTML/CSS/JS/images), with no server-side code**, and it scales automatically. To use your domain through Route 53, the **bucket name must equal the domain/subdomain** (`portal.example.com` → bucket `portal.example.com`), and Route 53 must be the DNS service (Alias record). Need HTTPS? Put CloudFront in front.

## Access Logs vs CloudTrail

**S3 Server Access Logs** record every request to a bucket, delivered as log files to *another* bucket. **THE trap: never log a bucket to itself** — each delivered log file is a new request, which writes a new log... an **infinite loop** that bloats your bill. Always a **separate target bucket**. Analyze the logs with **Athena** (SQL directly over files in S3 — no servers, pay per query).

| | S3 Access Logs | CloudTrail data events |
|---|---|---|
| Cost | Basically free (storage only) | Paid per event |
| Delivery | **Delayed**, best-effort | **Near real-time** |
| Detail | Request-level, complete | **Rich identity info** (exactly which IAM principal) |
| Pick when | "cheap," "complete record," "analyze with Athena" | "real-time," "who (which IAM user) accessed," compliance alerting |

**THE detail trap:** only **server access logs** record per-request fields such as the **referrer** and **turn-around time**, and they also feed billing/usage analysis. CloudTrail can't give you those. CloudTrail covers **bucket-level and object-level API calls** with identity.

## Performance

- Baseline: **3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second *per prefix*** — and unlimited prefixes. Need more throughput? **Spread objects across more prefixes** (that's what "add randomness/date partitions to key names" answers mean).
- **Multipart upload** — parallel chunks for big files: recommended >100 MB, required >5 GB, and a failed part retries alone.
- **Transfer Acceleration** — for **UPLOADS from users around the globe into ONE central bucket**: they upload to the nearest CloudFront edge location, then the data rides **AWS's private backbone** to the bucket. You **pay only if it's actually faster** than a normal upload. Signal: *"users worldwide upload large files to a central bucket, speed it up."* For global **downloads**, the answer is **CloudFront**, not TA.
- **Byte-range fetches** — GET just a slice of an object (`Range` header): parallel downloads, or grab only the header/footer of a huge file.

## Events and querying

- **Event notifications** — "when an object lands (or is deleted), do something": target **Lambda, SQS, SNS**, or **EventBridge** (EventBridge unlocks richer filtering and fan-out to many services). Classic: *"generate a thumbnail whenever an image is uploaded"* → S3 event → Lambda.
  - Event types: **object created**, **object removed**, **restore** (Glacier restore initiated/completed), **RRS object lost** (legacy class), **replication** events.
  - **`s3:ObjectRemoved:DeleteMarkerCreated`** fires **only when a delete marker is created** on a versioned object. It doesn't fire for `s3:ObjectRemoved:Delete`, which is a plain delete or permanent version deletion.
  - **THE fan-out trap:** each event notification configuration targets **exactly one destination**, and you can't have two configurations for the same event type with overlapping prefix/suffix filters. To deliver the same event to several SQS queues or consumers, send it to **one SNS topic and fan out** to the queues, or use **EventBridge**. Delivery is **at least once**.
- **S3 Select** — run SQL against the contents of **ONE object** (CSV/JSON/Parquet) and pull back only the matching rows — the app downloads kilobytes instead of the whole gigabyte. Signal: *"retrieve only a subset of data from a single large object."*
- **Athena** — SQL **across many objects/whole buckets**, serverless, pay-per-query. Signal: *"analyze/query logs stored in S3 with standard SQL."* One object → S3 Select; a data set → Athena.

## Question patterns

> *"Compliance data accessed about twice a year; auditors must receive it within 10 minutes. Most cost-effective class?"* → **Glacier Flexible Retrieval** (Deep Archive can never beat 12 hr; Instant passes but costs more; Flexible Expedited = 1–5 min).

> *"Records retained 7 years, almost never accessed, retrieval within 2 business days is acceptable. Cheapest?"* → **Glacier Deep Archive** (deadline ≥ 12 hr finally lets the cheapest class survive).

> *"Reports are heavily used for 30 days, rarely after 90, must always be retrievable in milliseconds."* → **Lifecycle rule: Standard → Standard-IA at 30 days → Glacier Instant Retrieval at 90** (known pattern → lifecycle; "milliseconds" keeps you in Instant, out of Flexible).

> *"Access patterns are unknown and unpredictable; minimize cost without performance impact."* → **Intelligent-Tiering** ("unknown/unpredictable" is its one and only signal).

> *"Thumbnails can be regenerated from originals at any time; store infrequently accessed copies cheaply."* → **One Zone-IA** ("can be regenerated" = single-AZ risk is acceptable).

> *"Processing artifacts are deleted after 20 days. Cheapest class?"* → **S3 Standard** (under every minimum duration — IA/Glacier would bill 30–180 days anyway).

> *"Security must audit exactly when each encryption key was used, and control key rotation."* → **SSE-KMS** ("audit key usage" is the KMS keyword; add S3 Bucket Key if the question moans about KMS request costs).

> *"Regulatory requirement: data must be impossible to delete for 5 years — even by administrators."* → **Object Lock, Compliance mode** ("even administrators" rules out Governance).

> *"Objects must be preserved indefinitely while litigation is pending."* → **Legal Hold** ("lawsuit" + no fixed end date).

> *"Users on every continent upload multi-GB video files to a single S3 bucket; speed up uploads."* → **Transfer Acceleration + multipart upload** (global UPLOAD to one bucket; global download would be CloudFront).

> *"All objects must be encrypted in transit."* → **Bucket policy denying requests where `aws:SecureTransport` is false** (in transit = HTTPS/TLS, not KMS).

> *"Enable access logging for a bucket — what's the key configuration rule?"* → **Deliver logs to a DIFFERENT bucket** (same bucket = infinite logging loop); query them with **Athena**.

> *"Replication was enabled but existing objects didn't copy over."* → **S3 Batch Replication** (CRR/SRR only replicate NEW objects).

> *"Expedited Glacier retrievals must be available whenever needed, with guaranteed throughput"* → **Purchase provisioned capacity** (each unit = ≥ 3 Expedited retrievals per 5 min, up to 150 MB/s).

> *"Lifecycle rule: move objects to Standard-IA after 7 days"* → **Not allowed. Standard-IA/One Zone-IA need ≥ 30 days in Standard** (Glacier transitions have no such floor).

> *"Partner account uploads objects into our bucket, but we can't read them"* → **S3 Object Ownership = Bucket owner enforced** (or require the `bucket-owner-full-control` ACL in the **bucket policy**). The uploader owns objects by default.

> *"Instances in a VPC must only reach approved S3 buckets"* → **VPC gateway endpoint policy** (one policy beats editing every bucket policy; S3 has no security groups).

> *"JavaScript on www.example.com must fetch images from a bucket on another domain"* → **Enable CORS on the bucket** (cross-origin permission, not public access).

> *"Need the referrer and turn-around time of every request to a bucket"* → **S3 Server Access Logs** (CloudTrail doesn't record those fields).

> *"Send an S3 event to two SQS queues"* → **S3 event → SNS topic → both SQS queues** (each event config has one destination; overlapping configs are rejected).

> *"Trigger only when a versioned object gets a delete marker"* → **`s3:ObjectRemoved:DeleteMarkerCreated`**.

> *"Keep archived data queryable by Athena at low cost"* → **S3 Standard-IA** (Athena can't read Glacier Flexible/Deep Archive without a restore).

> *"Host a static site at portal.example.com from S3"* → **Bucket named `portal.example.com` + static website hosting + Route 53 Alias** (bucket name must match the domain; static content only).
